## Camera Dock implementation (2026-10-16)

Camera Dock is an opt-in placement of the existing floating presentation controller. Its pure geometry uses the built-in screen's safe-area top edge and auxiliary-area midpoint, or the visible-frame top center when there is no usable built-in camera display. The non-activating panel is opaque, fixed in place, and joins Spaces/full-screen applications at floating level. It shares the existing playback session, snapshot, guide anchor, Timed Scrolling, Follow Voice, and app-local commands. The Output inspector, Present menu, View menu, and CommandMap expose the mode. Width defaults to 44% of display width and clamps to 360–760 pt; line count defaults to 3 and clamps to 2–5; horizontal nudge defaults to zero. Preferences are keyed by display UUID.

The first-use explanation states that the prompt appears in screen recordings, external camera placement is assumed, and CueGlass does not use the camera or microphone for Camera Dock. On external fallback when a built-in display is still connected, the grip indicates that the camera may be on another display. A vanished display or invalid fit pauses and closes the Dock while retaining the position; it does not choose another surface automatically.

M1–M12 are all **pending**: physical housing clearance, near-lens gaze, full-screen recorder behavior, non-activating keyboard use, VoiceOver, accessibility display settings, live display changes/clamshell, non-notched/external fallback observation, Timed Scrolling/Follow Voice hardware behavior, Get Info compatibility mode, screen-recording visibility, and macOS 14 runtime. Automated tests and the build do not count as these observations. See [ADR 0012](adr/0012-camera-dock-placement.md) and the Camera Dock section of the [manual plan](MANUAL_TEST_PLAN.md).

Automated verification on the available macOS 27.0.1 host with Xcode 27.0 (27A266a): the DebugLocal app builds for `arm64-apple-macos14.0`, all 81 CueFlowCore tests pass, all 103 native tests pass, strict Swift formatting passes, and Beans consistency passes. ## Optional Follow Voice implementation

Locale/model status checks do not open the microphone or download assets. The operator separately consents to model installation, can observe installation progress/cancel, and must explicitly Start after readiness. Microphone permission is checked/requested only after Start; a denial or missing usage description fails closed.

The adapter feeds bounded transient audio/results into on-device SpeechAnalyzer. `VoiceFollowCore` aligns transcript hypotheses to the immutable take's UTF-16 tokens; a measured TextKit 2 line table maps accepted tokens into Y positions. ## Follow Voice startup and inspector follow-up (2026-10-15)

Two captured macOS 27 crash reports for the operator's Start action ended in a Swift actor-isolation trap on AVAudioEngine's realtime messenger queue. The audio tap now uses a file-level `@Sendable` callback factory, keeping the hardware callback outside `SpeechVoiceSource`'s main-actor context. ## Spoken Follow Voice transport controls (2026-10-15)

English Follow Voice sessions accept commands prefixed with either wake phrase: “CueGlass, pause/resume/stop/stop following/stop take” or “Prompter, pause/resume/stop/stop following/stop take”. “Stop” means Stop Following. CueGlass may be transcribed as “CueGlass” or “Cue Glass”. A command fires at SpeechTranscriber's finalization watermark or after unchanged wording remains stable for 0.75 seconds; the short “stop” alias always waits through that window so “stop take” can complete. The bounded matcher withholds candidate command speech from script alignment. Pause freezes the shared timeline and suppresses alignment while leaving the explicitly authorized microphone stream active for Resume/Stop commands. Resume resets the alignment hypothesis at the last confirmed script token. Manual controls still close capture and take priority. Stop actions route through the existing operator controller actions.

Automated verification on macOS 27: the app builds for `arm64-apple-macos14.0`; all 48 CueFlowCore tests pass, including command finality/confidence/prefix spelling, bounded phrase timing, shared Speech attribute ranges, split-result and duplicate-result cases. The focused native VoiceFollow suite passes all 23 tests, including spoken pause/resume, alignment suppression during pause, manual seek takeover, and Stop Following/Stop Take routing. The full native run passed 78 of 79 tests; the sole failure is the pre-existing unrelated `OperatorFeatureTests.displaySelectionRemapsWhenDisplayIDChanges`, which left a synthetic reconnect selected as `disconnected`. Strict Swift formatting and `beans check --json` pass. The operator reported on 2026-10-15 that the pace adjustment works, while spoken commands still did not trigger. ## Contextual command channel follow-up (2026-10-15)

Since speech following works but commands still do not, English command recognition now uses a contextual DictationTranscriber result channel alongside the script SpeechTranscriber. The channels share the explicitly started SpeechAnalyzer capture; command-only results are isolated from script alignment. The command matcher retains three independent four-word hypotheses across incremental updates, so it can assemble a wake phrase and action delivered separately even when the product-name correction appears only in an alternative. It tracks each channel's finalization watermark independently. ADR 0010 records this design. Deterministic parser and native coordinator regression tests cover split results and cross-channel finality; live command recognition is still pending a human retest with the rebuilt DebugLocal app.
